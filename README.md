# Roll20 Embetterment — player-focused combat HUD

## Firefox-first browser extensions (v3.7.1 Firefox, v3.4.0 Chrome)

R20eb Firefox and Chrome are now **separate add-ons**, not a synchronized two-browser package. Firefox is the primary target: `npm run build:firefox` and `npm run check:firefox` build and test only Firefox. Chrome stays on v3.4.0 and uses the independent `npm run build:chrome` / `npm run check:chrome` workflow. Both share only the core Roll20 logic under `v3/`.

Firefox development, Mozilla unlisted signing, and GitHub-hosted update instructions: [Firefox guide](extension/firefox/README.md). Chrome can be updated later without bumping Firefox. Actual Mozilla-signed XPI distribution is **not yet active**; AMO API credentials are still needed.

## Original combined extension milestone (v3.4.0)

**Tampermonkey is no longer required.** Both Firefox/Floorp and Chrome/Chromium extensions run the existing v3 HUD, importer, token watcher and official sheet bridge on Roll20. Both are built from the same source modules as the optional userscript.

Download both extension packages from a passing [GitHub Actions build](https://github.com/newnetmp3/roll20embetterment/actions), or build them with npm run build:extension.

Firefox/Floorp: open about:debugging#/runtime/this-firefox and choose **Load Temporary Add-on**, then select the generated Firefox manifest (or unsigned ZIP). Standard Firefox requires Mozilla signing for permanent installation.

Chrome: unzip the Chrome package, open chrome://extensions, turn on Developer mode and choose **Load unpacked** for its extracted directory.

**Disable the previous R20eb Tampermonkey script first**, then reload Roll20. Using both injectors can create duplicate HUDs. [Full installation instructions](extension/README.md).

Packaging does not yet establish live verification of Roll20's private native attack and hidden-sheet behavior.

## Automatic character import (v3.1.0)

Enable **Auto-sync: On** once for your imported character. The choice and character ID are kept locally for that Roll20 game. The extension checks for its official D&D 2024 sheet and refreshes the imported data automatically. When the Journal sidebar exposes the matching character entry, the script uses Roll20's own double-click to load that sheet, moves **only that script-opened** dialog offscreen while it reads all the tabs, and then checks for changes periodically. It rejects mismatching character IDs and ambiguous same-name sheets, never moves an existing player-owned dialog, and does not clone Roll20's generic headless iframe (the generic iframe URL does not include a character ID).

If Roll20 hasn't rendered the Journal entry or doesn't open it via the normal browser double-click, auto-sync reports **Waiting for a matching journal entry**. Open Roll20's Journal sidebar once to make it available; in that case you may need to open the sheet once for Roll20 to load it. A player-opened visible sheet is read automatically without clicking Import, but its tabs are not switched behind your back. Quick current-view refreshes merge only observed live values into the previous full snapshot so the collected inventory, spells, and features aren't erased. The offscreen full scan runs no more than once every five minutes; current-view scans roughly every sixteen seconds on a scheduled eight-second poll. **New in 3.1.1:** while Auto-sync is enabled and a matching official sheet iframe or browser popout is mounted, a separate bounded HP-only request runs about every second. It reads visible, labeled current/max/temporary HP inputs without visiting tabs; changed HP values update the saved profile and preserve the inventory/spell catalog. Browser scheduling and iframe response time mean this is a best-effort interval, not a guaranteed sub-second update. If the official HP fields are unmounted, no HP value is fabricated. Turn Auto-sync Off to restore any offscreen dialog.

**v3.1.2 popout fix:** Automatic HP watching and current-view refreshing also work through a registered, official 2024 sheet opened in a separate browser window. The opener/editor bridge recognizes later Vue-loaded character names, prefers the matching popout over an older embedded copy, and drops closed popup references. A manually opened popout is never moved offscreen or switched across its tabs by auto-sync. For a popout, keep the original Roll20 editor window open and enable Tampermonkey on the official advanced-sheets domain in **both windows**. If the browser/extension removes the `window.opener` relationship (for example `noopener`) or blocks script injection, the cross-window bridge cannot communicate; live Floorp validation is still needed. The one-second cadence is best effort, especially for minimized/background windows.\n\nThis is a **browser-dependent, opt-in experimental feature**: its journal-open path is based on public DOM and needs live Floorp verification. No background data is guaranteed if Roll20 does not expose the necessary journal controls. Disable Auto-sync if it interferes with Roll20. The existing Read current tab and Import all tabs buttons remain available.

**v3.1.3 non-HP Auto-sync fix:** Automatic current-view imports now accept a recognized change to a skill, spell slot, resource, attack, spell, inventory item, feature, ability or save even if the currently displayed tab has no HP or other stats mounted. An empty result and mismatching character still fail closed. Updates merge into the prior complete import, preserving off-tab items; same-key entries update, but entries removed from an off-tab or virtualized list are not assumed deleted. Player-owned sheet tabs are never switched by Auto-sync. Current-view checks now use an eight-second scheduler with a twelve-second minimum gate (usually about sixteen seconds); HP remains around one second and script-owned background full-tab scans remain limited to five minutes. Live Floorp validation of non-HP field changes and unattended opening of a fully closed sheet are still required.\n\n**v3.1.4 event-driven synchronization:** The official 2024 sheet now sends a small, origin-checked change hint after a 350ms pause following edits to form controls or recognized increment/decrement buttons. Auto-sync in the original editor schedules a current-view scan after about 400ms, while enforcing a minimum of two seconds between heavier scans during rapid edits. This also works for an authenticated sheet popup, without switching the player's current tab. The ~16-second current-view polling remains as a fallback for Roll20 changes that do not emit observable browser input/change events (including some programmatic updates). The HP-only watcher remains roughly one second. Disabling Auto-sync cancels queued change scans; forged or ambiguous popup messages cannot trigger them. Browser background throttling and the duration of Roll20's own update/render cycle can still increase latency. Live Floorp verification remains required.\n\n**v3.1.5 Inventory controls and debug updates:** In v3.1.4 the automatic `current` scan identified its tab merely as `Current view`, so the 2024 generic item-row adapter skipped real inventory rows. The reader now detects the active primary tab using visible official tab state. Importing an inventory row also captures explicit quantity/incrementer values, including `0`, and observed native checkbox, switch and aria-pressed states. Inventory debug details display these structured raw observations rather than relying on the row's unchanged text. The change watcher recognizes inventory-toggle clicks as well as input/change events. A toggle's specific meaning (e.g. equipped, used, active) is **not inferred** from the raw state. As before, a filtered/virtualized item absent from the rendered DOM is not automatically deleted from a saved inventory because absence isn't proof of deletion. Live Floorp/official 2024 sheet validation remains needed.\n\n**v3.1.6 inventory quantity-zero removal:** If an explicitly labeled inventory quantity/incrementer reads numeric **0** in the current official sheet, that item disappears from R20eb's **imported Inventory list** (including count/JSON export). It is **not deleted from Roll20**; this importer is read-only. Later positive quantities add the item back. Applies to auto-sync, manual current/all-tabs imports and old stored snapshots. A missing item on another tab, behind filtering or virtualization, is not interpreted as zero and will not be removed. Raw reader scans intentionally retain explicit zero observations as deletion signals until the editor publishes its filtered snapshot. Item toggle On/Off support from v3.1.5 stays unchanged. Browser confirmation of actual Nier item behavior is pending.

**v3.1.7 live screenshot-driven quantity fix:** The player confirmed an On/Off Inventory toggle works but provided a screenshot showing **Crowbar at 0** in the official 2024 sheet and still present in R20eb Inventory; its debug panel showed only `headlessui-switch-100 On`. This demonstrated that the zero-count removal in v3.1.6 could not fire without a recognized quantity observation. The Inventory reader now prefers an item's complete row wrapper (not a nested item-title sub-element), and it detects a unique unlabeled numeric input located in a bounded **minus / input / plus** stepper, without treating arbitrary numeric controls as an item quantity. Changes from unlabeled ± buttons also trigger the authenticated current-view refresh. Inventory debug now explicitly reports **Quantity not detected** if it captured a toggle but could not identify a quantity control. Numeric zero still removes the item from R20eb's imported list (never deleting or writing Roll20 records); changed positive counts allow reappearance. Regression tests recreate the screenshot's unlabeled Crowbar counter and include negative cases for ambiguous/missing buttons. Live Floorp confirmation on the actual item remains required.

## v3.3.4 — Roll20 current-player identity and selected token repair

**Live user regression:** With their own linked player token selected, the v3.3.3 HUD displayed **"Cannot verify a unique character you control in Roll20. Select its token first."** The background opener aborted before invoking Roll20's sheet UI.

**Identified code fault:** The addon only looked for player ID under `d20.player`. Roll20's browser editor commonly exposes the logged-in player instead as `window.currentPlayer.id` (and as a Backbone model whose `.get('_id')` is populated). The shared permission resolver now checks the real browser `currentPlayer` first, with guarded fallback to other existing client fields, and reuses that same verification for both selected-token HUD detection and background native-sheet opening. The opener reads the **currently selected token's represented character** directly when invoked, so a valid selection still works before the HUD's 400-ms token watcher catches up. The exact character ID disambiguates same-name PCs.

Character control remains mandatory: `controlledby` must explicitly include the current Roll20 player ID or `all`; merely appearing in the Journal, being selected, or being a GM is not treated as proof of permission. Both comma-separated and array-shaped exposed permissions are recognized. Missing in-browser objects, ambiguous characters, and genuinely unowned sheets still fail closed. Instead of one misleading generic error, each case now says whether the editor player ID, character model, linked token, same-name identity or **Controlled By** permission was unavailable.

**To verify in Floorp:** Update the userscript and reload Roll20 (no manual character sheet open), select one of your controllable linked tokens, open a HUD attack, and choose **Find native Roll20 attack**. If the background sheet opens and the matching button is found, confirm the roll and check Roll20 Chat. If the prompt still fails, send the **exact new status**: it distinguishes which editor field is missing so the remaining issue can be corrected without bypassing access checks. Roll20's internal `view.showDialog()` is still a browser-dependent feature; automated mocks cannot verify the real UI mounting behavior.

## v3.3.3 — HUD-owned background official character reader

**No need to manually open your official Roll20 character sheet for each native attack, where Roll20 exposes its in-browser sheet opener.** When you press **Find native Roll20 attack** and no matching official reader is open, R20eb resolves your own character from the current Roll20 player-controllable linked token (or a uniquely named, player-controlled character from the campaign's in-page model). It uses Roll20's own browser-side character `view.showDialog()` method; if unavailable, it tries the exact identified visible Journal row. It records dialogs that existed *before* the request and adopts **only one newly created, character-ID-matched dialog**. The HUD-owned dialog is moved offscreen without disabling its Vue-rendered inputs. An overlay created by that same request is made nonblocking. It does **not** move, close, reparent or navigate sheets opened manually by the player.

The authenticated iframe reader uses its already-established origin/source verification to locate attack buttons. The addon may switch to Combat **only within a verified HUD-owned or previously Auto-sync-owned background sheet**; a player-opened sheet's tab is never changed. Existing per-character background sessions may be reused when switching between multiple controllable tokens, with a conservative six-session limit. Attacks still require a uniquely identifiable name/source and **two separate user steps**: inspect, then confirm one native to-hit click with the time-limited token. No fabricated attacks, silent casts, equipped changes or automatic turns are performed.

**Roll20 compatibility and fallback:** The opener is an internal browser-side feature, not an officially stable API. If it is missing, if the character isn't demonstrably controlled by the current player, if the session cannot be uniquely identified, or if a same-character manual dialog is already open on another tab, R20eb reports a useful blocked status and leaves the existing UI unchanged. We do not clone an arbitrary official iframe URL or bypass Roll20 session/character permissions. Background operation needs a real Floorp test; a passing simulated DOM test cannot prove that the current 2024 character model exposes the same dialog methods. If it fails in your game, share the exact HUD status; the manual sheet remains a safe fallback.

## v3.3.2 — Source-identified native attacks and actual 2024 hit buttons

Live user screenshots showed two distinct failures after v3.3.1: opening the **first Dagger** card returned "Choose a unique attack from the imported character" because the import currently contains more than one attack named Dagger; a **Handaxe** probe found the correct row but rejected the official **"+7 Attack"** control alongside its **"1d6+4" damage** control.

This release changes the HUD's native-action button to address the **unique imported attack _key**, not just a potentially repeated display name. The reader receives both the selected character's name, attack name, item key, and source-observed attack text, and uses the actual **attack bonus and damage notation** as evidence when several visible official Combat rows share one name. Identical rows with insufficient differentiating evidence remain blocked rather than arbitrarily choosing one. This works for any player's own sheet, not just Nier.

On the official D&D 2024 sheet, a button labeled **"+7 Attack"** (other signed numeric bonuses supported) is now eligible as the native **to-hit** button inside the one uniquely matched attack row. The separate damage-dice control such as "1d6+4" is never mistaken for an attack. Explicit standard "Roll Attack" labels are still supported. Probe and confirm pass the same attack identity and source metrics; confirmation rechecks the current native row/button and blocks replay, changed bonuses, wrong characters, wrong rows, or changed source data. All native clicks still require **explicit second confirmation**, and no success is claimed unless the official sheet really produces a Roll20 chat roll.

When multiple imported cards share the same display name but refer to distinct weapons or variants, their displayed names may be identical while their underlying roll signature is not. If the source contains no distinguishing roll evidence or matching native row, the native bridge fails closed and reports the ambiguity. The importer, selected-controllable-token support, per-character HUD loadouts, and read-only spell/item functionality remain intact.

## v3.3.1 — Last selected controllable token and attack probe diagnostics

The HUD now tracks the last newly selected Roll20 map token which has a linked character controlled by the logged-in player. Its image, name, character stats and action catalog become the HUD's active character, and quick loadouts are persisted per represented character ID (within the same game). Other players' tokens and unlinked graphics are ignored. A never-imported character shows a blank named HUD and prompts importing its own official sheet; no other PC's HP/attacks are reused. Duplicate-named characters cannot silently inherit each other's legacy snapshot. Auto-sync's previous in-flight scans and pending native confirmation are invalidated on character switch. This is read-only; token movement and sheet permissions are unchanged.

**Attack probe issue:** The user reports v3.3.0 fails to locate *any* native attack. Its selector recognized fewer generic item-row/title elements than the importer and demanded button text literally saying Roll Attack. ## v3.3.0 — Optional native Roll20 attack pilot (character-agnostic)

R20 Embetterment supports **the player's imported D&D 2024 character**, not Nier or any other fixed sample character. All names, attack entries, equipment, stats and roll requests come from the current imported sheet and authenticated live official character window. Nier is only one test fixture. Regression tests exercise multiple unrelated character names and distinct attack inventories, reject mismatches, enforce one-time confirmation, and confirm switching characters does not retain a previous Auto-sync character-ID pin.

The first experimental native action integration is available by expanding an **imported Attack card** in the Actions flyout and choosing **Find native Roll20 attack**. It contacts the player's exact matching open official sheet through the authenticated cross-origin reader, requiring a **visible Combat tab** and one uniquely named attack row containing one **explicitly labeled native Roll Attack button**. If a verifiable button is found, the HUD prompts for **Confirm native roll**; only that second click instructs the official sheet to click its button once. A single-use token expires after 15 seconds and cannot be reused; any missing, ambiguous, hidden, changed, mismatched or different-character control fails closed. This is **not** a generic macro, spellcasting or game-state API, and there is no fabricated dice formula or automatic resource expenditure.

**Important live QA boundary:** Roll20 may render its official 2024 attack controls with different labels than the narrow accepted `Roll Attack` control. In that case the experiment reports a clear blocked status and **does not click anything**. Do not widen selectors speculatively; inspect the relevant real character's attack button structure before broadening. A successful `clicked` response confirms only a DOM click was dispatched, not that Roll20 produced a chat roll. Verify the actual chat result manually. Spell casting, targeting, End Turn and automatic action expenditure remain read-only.

Previous importer, Inventory quantity-zero removal, character source attribution, live HP, HUD layout, and Debug functions remain intact.

## Argon faithful port direction — v3.2.2

Original reference: [Argon Combat HUD Wiki](https://wiki.theripper93.com/free/enhancedcombathud) and core implementation [theripper93/enhancedcombathud](https://github.com/theripper93/enhancedcombathud), with the first-party D&D 5e system adapter [theripper93/enhancedcombathud-dnd5e](https://github.com/theripper93/enhancedcombathud-dnd5e). The previous Twilight: 2000 ZIP is only one compatible adapter, **not** the complete original HUD. Our target is an **independent Roll20 port of the visible Argon UI and behavior**, not a generic CRPG-inspired panel or Foundry runtime embedded in Roll20. Source licensing and attribution must be reviewed before reusing original assets or code; this implementation uses original HTML/CSS/SVG and captured user data.

The default HUD now follows the original wiki's bottom-aligned horizontal composition rather than a centered card layout. Six local quick slots appear above the portrait as three two-slot weapon loadouts, plus a saves/skills/tools flyout. Large square action controls are grouped into **MAIN ACTION / BONUS / FREE / REACTION / PASS**, with a smaller secondary text bar for local action tracking. The **CAST SPELL** control expands an upward flyout grouped by observed spell level; if the sheet provides slot counts, the flyout displays remaining and maximum counts. Items and features also open upward catalog flyouts. The full importer remains under Debug. The wiki's **Shift+A** keyboard shortcut toggles the HUD outside text inputs.

The six quick slots are configured by clicking one and selecting an already imported attack, spell or item. These assignments are saved per Roll20 game and do **not** equip/unequip anything in Roll20; drag-and-drop from a separate character sheet is not yet implemented. Action markers are **manual local indicators**; the Reset tracking button clears them, and reopening the HUD also resets them. No attacks, saving throws, casts, movement tracking, targets, macro executions or End Turn actions are dispatched to Roll20 yet. The PASS tile is deliberately disabled until native end-turn behavior is verified. Explicit tooltips explain controls remain read-only.

**Parity still to implement after browser QA:** actual token selection/actor portrait, native rolls/casts, action-use tracking tied to successful native events, the targeting picker, Foundry-style drag/drop weapon-set behavior adapted to Roll20, movement and dash tracking, item tooltip details, spell preparation controls and per-character configuration. Floorp/Firefox verification remains required even though Argon itself was originally designed for Chrome.

## HUD v1 — Argon-inspired v3.2.1

**Reference correction:** The user-provided `enhancedcombathud-t2k4e-3.0.0.zip` is a *system adapter* for the separate Argon Combat HUD core, **not** a standalone theme or Foundry UI source. Its class hierarchy uses a PortraitPanel and separately segmented Slow/Fast/Free action panels. The previous wide card grid was not faithful to that structure. This release changes the default view into a compact centered portrait dock, observed hit-point bar and side stats, explicit Action / Bonus Action / Reaction icon groups, short resource strip and category tabs. The comprehensive expandable card list is now an **on-demand drawer**. Buttons navigate the local read-only catalog; there is no Foundry runtime dependency or copied asset library.

**Missing-stats correction:** The existing Nier JSON export contains AC `17` and Speed `55` as UUID-addressed input observations with the *exact* captured adjacent captions `ARMOR CLASS` and `SPEED (ft)`. These values were never placed in `stats.ac` / `stats.speed`, which made the new HUD display dashes. On importing/loading a snapshot, R20eb now reconciles these **only when the nearby caption is exact and observed values agree**, including already-saved snapshots. It does not guess from UUIDs or coincidentally equal numbers. The saved Nier export does not contain labeled authoritative Passive Perception; when an actual Perception skill modifier is available, the HUD displays `PASSIVE BASE` as `10 + observed Perception modifier` with a tooltip explaining that situational bonuses are not included. It does **not** store this calculated base as official sheet data.

## HUD v1 — v3.2.0

The first combat HUD is now the **default interface**, with the previous sheet importer and JSON diagnostics preserved behind the HUD's **Debug** control. The working authenticated official D&D 2024 sheet reader, popout support, HP watcher, event-driven change hints, and zero-quantity inventory removal all remain active. The reader and data store have not been replaced.

The HUD is a bottom-center, responsive, antique-metal/dark combat strip inspired conceptually by CRPG/Foundry interfaces; no game artwork or Foundry runtime dependencies have been copied. It displays only **observed** character name, current/max HP with a proportional bar, AC, movement speed, initiative, passive perception, spell-slot data, and named resource controls. Unknown values show **—** instead of guessed numbers. Action categories are **Actions, Bonus, Reactions, Spells, Inventory, Features and Resources**, populated from the imported attack/spell/feature/item/resource cards. Only explicitly observed spell casting times or feature action-type metadata are used to classify Bonus Actions or Reactions.

Cards can be expanded for details; they are **read-only in HUD v1** and do not roll, cast, spend resource charges, change action economy or write to Roll20. This safety boundary is intentional until verified native action integration is implemented in a later HUD milestone. HP and card changes repaint the HUD from the same importer snapshot; Sync controls the existing auto-sync system. Minimized state and selected HUD category are remembered per game. The full importer remains accessible for troubleshooting through **Debug** and is not visible by default. Initial character import still requires a supported Roll20 reader; fully closed-sheet Journal opening is not yet user-verified.

**Live QA:** After installing, reload both Roll20 editor and the official popped-out 2024 sheet, import once through Debug if no snapshot is saved, enable Sync and confirm the HUD HP bar and Inventory/Actions change without manually opening Debug. No native combat rolls should be triggered by card expansion.

## Install and use
Install or update the script from https://raw.githubusercontent.com/newnetmp3/roll20embetterment/main/roll20-embetterment.user.js. Disable duplicate/old scripts and reload Roll20. Open an official D&D 2024 character sheet. The new importer appears at the bottom right of the editor. Refresh the sheet list, choose the visible sheet, then use **Read current tab** or **Import all tabs**. The latter navigates rendered tabs and sub-tabs and restores the original tab selection.

## What the new engine captures
- Labeled form values: current, max and temporary HP, AC, speed, initiative (including decimals), six abilities, modifiers, saving throws, skill bonuses, spell slots, level, proficiency, spell bonuses and other identifiable numeric fields.
- Named spells, attacks, inventory, features, resources and skills when those cards are rendered; spell/card text, casting metadata hints and accessible action labels.
- Raw labeled but unrecognized control values in **Fields**, explicit source information, coverage counts, rejected/hidden counters, scanned tabs and limits in **Diagnostics**.
- A local per-campaign snapshot and downloadable JSON export; missing values are **not** replaced with default stats.

This is a player-triggered, read-only scan. It never writes to Roll20 character values, accesses private application state or fetches data from external servers. The iframe and editor communicate via strict origin-checked postMessage. Hidden/headless frames are not treated as a player's open sheet. Bounded traversal avoids hanging the browser.

## Limits
This v3 baseline intentionally supports the official D&D **2024** sheet first; the old combat wheel and the 2014 sheet adapter will return in separate milestones. Roll20 may virtualize or lazily load cards: only rendered DOM values can be collected. All browser integration still needs a live Floorp test; DOM fixture tests cannot establish that the userscript actually loaded inside Roll20's iframe.

Production only bundles v3/00_capture.js, v3/10_reader.js, v3/20_ui.js and v3/30_boot.js. Run npm run check (build, tests, syntax). The v2 implementation remains unexecuted in src/ and its legacy test suite remains for archival regression reference.
